# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, no-bundler browser demo for the Authenticate 2026 conference: Swissbit iShield USB keys (raw WebAuthn) combined with Ideem's ZSM / Passkeys+ SDK. Plain ES modules served as-is; there is no framework, no transpiler, and no linter configured. Everything an attendee reads calls the hardware a **FIDO key**, never an iShield key (the owner's request, 2026-10-13); file names, identifiers and storage keys keep `ishield`. On the demo page the status pill, the SNA indicator and the challenge section label go further and say **USB Key**, and the number pill and indicator say **Phone# Verified** (2026-10-13). `.gitignore` excludes `tests/`, `test-results/`, and `playwright.config.js`, so any Playwright tests are local-only and not part of the repo.

## Commands

```sh
npm install              # postinstall runs `npm run build`
npm run build            # node build.js -- copies SDK + qrcode-generator + jsqr from node_modules into vendor/
node dev-server.mjs      # http://localhost:8080 (PORT=3000 to change)
./run.sh                 # bare python http.server fallback; no /db proxy, no /log
```

`vendor/` is git-ignored and must exist before any page loads: `index.html` resolves `@ideem/zsm-client-sdk` through an import map to `./vendor/@ideem/zsm-client-sdk/ZSMClientSDK.js`, `app.js` and `register.js` dynamically import `./vendor/qrcode-generator/dist/qrcode.mjs`, and `register.html` loads `./vendor/jsqr/dist/jsQR.js` as a classic script (a UMD bundle that sets `window.jsQR`; `register.js` reads the global). If a page 404s on an import, run the build. Adding a new npm dependency that a page imports means adding it to the `packages` list in `build.js` as well.

Use `dev-server.mjs`, not `run.sh`, for anything touching the user database or the P2P exchange: only the Node server proxies `/db/*` and mounts `/api/exchange`. It also accepts `POST /log` (appends to `.dev-logs/fido-test.jsonl`) and `GET/POST /credentials` (shared list in `.dev-logs/credentials.json`); both are dev-only and silently absent in production.

Testing on a phone needs HTTPS. A Cloudflare quick tunnel works; the hostname changes every run, so credentials made under it are bound to that hostname only:

```sh
cloudflared tunnel --no-autoupdate --url http://localhost:8080
```

## Vercel deployment

Production is `https://authenticate26.vercel.app`, deployed from GitHub (`useideem/authenticate26`, branch `main`). There is no `.vercel/` link in this checkout and no Vercel CLI installed; push to deploy. `vercel.json` sets `outputDirectory` to `.`, so the whole repo root is the static site, including `api/db.js` source and `zsm_app_config.json`.

There are two serverless functions. `api/db.js` is a proxy to the Ideem user API at `https://sbit.authconcepts.com:3033/api` (override with the `DB_API` env var). The rewrite in `vercel.json` maps `/db/:path*` to `/api/db?path=:path*`. Two constraints were measured on real deployments and must be kept:

- **Flat file, path in the query.** A catch-all `api/db/[...path].js` matched only one path segment on Vercel (`/api/db/users` worked, `/api/db/users/9999` returned Vercel's NOT_FOUND). Keep the function at `api/db.js` with nothing dynamic in its name and pass the remainder as `?path=`.
- **A function, not a plain external rewrite.** Vercel does not document non-standard ports (`:3033`) in rewrite destinations. A server-side fetch has no such ambiguity.

`dev-server.mjs` implements the identical proxy in `handleDb`, so pages always fetch the relative path `./db/...` and work unchanged on localhost, a tunnel, and Vercel. Change the two together. The one answer either changes (since 2026-10-19): a `GET /users/phone/:value` the upstream answers 404 is matched on bare digits against the whole list and answered as the route would, an array of the matching records, first match first (`matchByDigits` and `phoneLookupValue`, exported by `api/db.js` and imported by the dev server, and by `api/exchange.js` for its own contact lookup, which calls the upstream itself). The attendee list the owner loaded that day holds 108 of 251 numbers formatted, `(212) 614-6927` or `+44 7511 509261`, which the exact-string route can never find from the bare-digit User ID the booth QR gives the phone, so until then those attendees had no balance, no contacts and no saved exchange. The records are left as loaded; two of them share a number, and the first in the list wins, as it would on the exact route. The same goes for the redirect from `/enroll.html`, the booth page retired on 2026-10-12, to `/register.html`: `vercel.json` answers it with a 307 and the dispatch in `dev-server.mjs` does the same.

The second function is `api/exchange.js`, the P2P Contact Exchange matchmaker, reached at `/api/exchange` with no rewrite. It is one flat file for the same reason as the proxy, dispatching on method and the `?code=` query: `POST` without a code creates an exchange for `{ userId }`, `GET ?code=` is what the initiator's page polls, `POST ?code=` completes it for the responder's `{ userId }`, and a bare `GET` is a health check. It answers 404 for a code it does not hold (never issued or expired) and 409 when the code was already completed, and the page branches on exactly those two. Contact fields are read from the user API by bare-digit phone (matched on digits against the whole list when the exact route 404s, `matchByDigits` from `api/db.js`, since 2026-10-19), never taken from the browser; a User ID with no record still exchanges, with `found: false`. Each contact also carries the record's integer `recordId`, and a completion writes the exchange to the user API's exchanges table (`POST /exchanges` `{ senderId, receiverId }`, by record id, one row in each direction because the API's contacts are one-directional and the demo's exchange is mutual; the route is the owner's of 2026-10-14, measured in `docs/user-api.md` §3c). The record's `upstream` field (`{ saved, exchangeIds, reason }`) reports it: a side with no record, a refused POST or a database that does not answer within `UPSTREAM_TIMEOUT_MS` gives `saved: false` without blocking the exchange, and nothing retries. Since 2026-10-18 a completion also pays for the contact: before the rows go up the function reads both contact lists (`knownContacts`, paged through `GET /users/id/:id/contacts`, one entry per sender however many exchanges), then credits each side `NEW_CONTACT_POINTS` (100, with `partner: "IDEEM"`, a `PATCH /users/:id/balance` straight to the user API) when its row landed and the other person was not already on its list; the record's `points` field (`{ amount, initiator: { credited, code, balance, detail }, responder: {…} }`, the codes `new`, `known`, `unread`, `unsaved`, `no-record` and `failed`) says what each side got and why, and a failed credit is never retried. The credit is the function's rather than the pages' so both sides get it exactly once per completion, which the claim key already makes single-use, whether or not their page is still open; `UPSTREAM_TIMEOUT_MS` is 2.5 seconds so the four rounds of calls a completion now makes stay inside a ten-second function. The page draws that as a line under the other person's card and then lists this attendee's contacts from `GET /db/users/id/:recordId/contacts` (`renderContacts` in `app.js`, hidden when empty or unreadable). Records expire after `EXCHANGE_TTL_SECONDS` (default 600). The store is Redis through Upstash's REST API when `KV_REST_API_URL` and `KV_REST_API_TOKEN` (the Vercel Marketplace names) or `UPSTASH_REDIS_REST_URL` and `_TOKEN` are set, with or without the `PREFIX_` a Custom Prefix on the Vercel connection adds, otherwise a process-local Map. The health check at `/api/exchange` reports `store`, the variable that supplied the Redis URL, and the names (never values) of every Redis-looking variable the deployment can see; open it first whenever the page shows the memory-store warning on Vercel. The Map is correct on `dev-server.mjs`, which imports the function and mounts it at the same path, but on Vercel it is only a fallback: the initiator's poll and the responder's completion can reach different instances, so every response carries `store` and the page shows a warning when it reads `memory` off localhost. Add Upstash Redis to the Vercel project for the real thing. The ZSM token is deliberately never sent to this function: the SDK's validate-token window is a few seconds and the call stays inside `umfa.js`, so the function trusts the User ID it is given.

The upstream API has no authentication and no CORS headers. Its measured behaviours (exact-string phone matching, PUT replaces rather than merges, duplicate phones allowed, PATCH balance is an additive ledger adjustment that permits overdrafts and, since 2026-10-16, refuses a body without a `partner` string) are in `docs/user-api.md`. Read it before touching any `/db` call. The full route list is the owner's Postman export at `docs/IdeemAPI.postman_collection.json`; it names the 15 routes but has no responses or PUT bodies, so the markdown doc is the behavioural reference and the collection is only the map. A second export, `docs/IdeemP2P.postman_collection.json` (2026-10-14), maps the seven exchange and contact requests the same way.

Users are keyed two ways: phone number and badge confirmation number (`/users/conf/:confNumber`). The confirmation-number routes are case-insensitive, the lookup returns an object rather than an array, and only that route and the write-response bodies carry the `confNumber`, `Company`, and `email` fields; list, by-id, and by-phone reads omit them. Since 2026-10-14 `POST /users` stores `Company` and `email` (measured with a throwaway record; the PUT routes still ignore both, and no read we can make returns them, because the by-confirmation read needs a number). No write route stores `confNumber`, so the API cannot assign a confirmation number: the PUT by confirmation number only updates a record that already has one and 404s otherwise, despite the collection calling it "Create". The balance PATCH by confirmation number is the same additive ledger adjustment as the other balance routes. The owner's test user `KVNLHY66K2P` must never be replaced or deleted.

## Module layering

```
app.js / fido-test.js / register.js      page glue, DOM, screens, flash messages
   |           |              |
   |           |              +---- key-enroll.js   the discoverable create that writes a key, as a function
   |           |                        |      |
   |           +---- webauthn-util.js <-+      |     CBOR decoder, authenticator-data parser, RP-side checks
   |                         |                 |
   +---- umfa.js             |                 |     Ideem UMFAClient wrapper; the only module that imports the SDK
   |        |                |                 |
   +---- ishield.js <--------+-----------------+     raw WebAuthn for the key; zero SDK deps; also base64url + SHA-256 helpers
   |
   +---- sna.js                          simulated Silent Network Authentication; no DOM, no network, no SDK

partner.js ---- ishield.js (webauthnIdentify) and key-enroll.js (detectBrowser only)      the partner page; talks to /db itself
```

- `ishield.js` and `umfa.js` are the partner-facing integration code and never touch the DOM. Keep UI concerns in the page scripts.
- `sna.js` is a simulation of IDlayr's Secure SNA flow (`https://secure-sna-demo.idlayr.com`), with the same no-DOM rule. `verifyNumber(phone, { scenario, onStep, speed, signal })` plays six timed steps and resolves to `{ match, checkId, code, reason, verifiedAt, steps }` without any network request; the scenarios are `success`, `nomatch` (fails on the PATCH with `match: false`) and `unsupported` (stops at the network step). The step wording is `SNA_STEPS` and the page draws its list from it: the labels only, since 2026-10-14 (the `detail` and `failDetail` strings naming the API call behind each step stay in `sna.js` as the record of what the step stands for, but the owner wanted them off the screen). `isNumberVerified` / `setNumberVerified` / `getNumberVerification` keep a per-device marker, `sna_verified:<user>` in `localStorage`, that a successful check writes, or that a browser rebound from the user's passkey carries over without a check (`{ carriedOver: true }`, since 2026-10-18). A real integration replaces the inside of `verifyNumber` with calls to a backend holding the IDlayr key; nothing in `app.js` changes.
- `umfa.js` loads `zsm_app_config.json` at module init and caches one `UMFAClient` per `consumer_id`. `initializeZSMClient(user)` must precede `checkAllEnrollment`, `enroll`, and `authenticate`; `resetClient()` on logout. `enroll` and `authenticate` call `validateToken` automatically, and an enrollment is not activated until that POST succeeds.
- On any `localhost:<port>` origin, `umfa.js` zeroes every hex segment of the config and sets `application_environment` to `TEST`, so the SDK initialises without real credentials. Any other origin (tunnel, Vercel) uses the real values in `zsm_app_config.json`.
- `state.js` is a classic (non-module) script exposing a global `State` Proxy. The demo only uses `STATE.loginID` and `STATE.reset()`; the `stateChange` events it dispatches are unused.
- The README's quick-start still shows a `@ideem/plugins.passkeys-plus` side-effect import. That package was removed; `umfa.js` imports only `UMFAClient` from `@ideem/zsm-client-sdk`, and the SDK is pinned to `latest` in `package.json`.

## WebAuthn constraints that are not negotiable

These came out of two days of measurement on real keys and browsers (`docs/ishield-pinless-discoverable.md`). Breaking any of them breaks retrieval on attendees' phones.

- **Demo keys must stay PIN-less.** Any PIN makes every browser prompt for it, even with `userVerification: 'discouraged'`.
- **Enroll in Safari on a Mac, never desktop Chrome.** Chrome upgrades a discoverable create on a security key to UV-required and forces PIN setup. `register.js` warns on screen when `detectBrowser` in `key-enroll.js` reports desktop Chrome.
- **Enroll on the production origin.** Credentials are bound to the RP ID (hostname). Keys enrolled on localhost or a tunnel are invisible to the Vercel site. The QR code points at `location.origin`, except from localhost, where it points at `PUBLIC_DEMO_ORIGIN` in `register.js` and shows a warning that the credential will not be found there.
- **Create options** (`createOptions` in `key-enroll.js`, the only copy since the booth page `enroll.html` was retired on 2026-10-12; `fido-test.js` defaults its controls to the same values): `residentKey: 'required'`, `userVerification: 'discouraged'`, `credentialProtectionPolicy: 'userVerificationOptional'` **without** `enforceCredentialProtectionPolicy` (Chrome throws `NotSupportedError` on that pair), `hints: ['security-key']`, `attestation: 'none'`. `enrollKey` records each credential in the `localStorage` list `ishield_enrollments` and builds `excludeCredentials` from it; records the booth page wrote there still count. `webauthnEnroll` in `ishield.js` is a different ceremony (`residentKey: 'discouraged'`, the create the demo page's Trust Device ran until 2026-10-14) and is not what writes a key for retrieval; no page calls it now, and `app.js` imports only `webauthnAuthenticate`.
- **Get options** (`webauthnIdentify` in `ishield.js`, which `webauthnAuthenticate` wraps with the expected-user check): empty `allowCredentials`, `userVerification: 'discouraged'`, `hints: ['security-key']`. The empty list is what lets a stranger's phone read the key, and it is what desktop Chrome refuses on a PIN-less key. Phones (iOS any browser, Android Chrome 128+) are the target; desktop Chrome would need an ID list capped at 64 entries, which is not implemented.
- **Phone numbers are bare digits everywhere**: on the key as `user.id`, in the database, in the `?userid=` parameter, in lookups. `normalizePhone` (`register.js`) and `phoneDigits` (`app.js`) apply the same rule: strip non-digits, drop a leading US `1` from an 11-digit number. Format for display only. The user API does not enforce this: the owner's test user carried `512-555-1234`, and the list loaded on 2026-10-19 holds 108 formatted numbers, so `register.js` normalizes the phone it reads back before putting it in the QR, and since that day the `/db` proxy and the exchange function match a by-phone lookup on digits against the whole list when the exact match 404s (the Vercel section).
- **The key is the authority on identity.** After a successful get, `reconcileUserId` in `app.js` compares the typed User ID with the `userHandle` the key returned. A different number stops the flow; a different spelling of the same number is rewritten to the key's form; a key that returns no handle stops it too (since 2026-10-13; before, the typed value stood). The key is asked for the first time and after a suspension, never otherwise (the owner's rule, 2026-10-13): `login()`, the only ceremony on the demo page since the New toggle went on 2026-10-14, runs the open get only on a device with no ZSM credential for the typed User ID (then binds it through `bindDevice`) or a suspended one (then reactivates it), and a bound, active device logs in on the passkey alone. Since 2026-10-18 a browser storage area with no ZSM credential for a number whose passkey Ideem's server already knows (`checkAllEnrollment` reports `pkpCredential`, the server's challenge for that passkey; the state of a private tab, another browser on the phone, a second device on the same keychain, or this phone after Reset Device) is rebound by the passkey alone, `bindWithPasskey`: the SDK's enroll in its `required` mode authenticates the existing passkey and rebuilds the ZSM share, no dialog and no key, and a cancelled or absent passkey falls through to the key path; the key and number markers it writes say `boundFromPasskey` and `carriedOver`, which the pills read as false. The mode matters: in the `preferred` mode the demo's other enrolls use, a cancelled passkey sheet falls back to a ZSM-only enrollment with no proof, which is safe only after the key has vouched. So the key is asked only where there is no passkey to ask instead. Nothing on the demo page writes a credential to a key any more: a get that fails with NotAllowedError (dismissed, timed out, or nothing on the key for this site) says to enroll the key on the registration page. The mismatch check still covers a stranger on a bound phone: the ZSM credential is looked up per User ID, so a different number has none, lands in the binding path, and meets the key there.

## Registration page (`register.html`)

`register.js` is page glue with no SDK or WebAuthn involvement. Register calls `getUserMedia` (`facingMode: 'environment'` as a preference, so a laptop's single front camera is what it gets) and decodes frames on a 150 ms timer until one holds a QR code, then stops the stream before anything else happens. The decoder is chosen once: the browser's `BarcodeDetector` when `getSupportedFormats()` includes `qr_code` (Chromium, backed by Vision on macOS), otherwise the vendored jsQR on a canvas copy of the frame scaled to 640 px wide; Safari has no `BarcodeDetector`, so there it is always jsQR. The decoded text is trimmed and used as-is as the confirmation number: `lookupAttendee` reads `/db/users/conf/:confNumber` (case-insensitive upstream, a single object back, 404 means no attendee), and the page shows name, phone and email with "not on record" for blanks. The lookup runs under `dbSignal`, which gives up at `DB_TIMEOUT_MS` (6 seconds, since 2026-10-19, after a venue where it hung with no way past it): a database that does not answer, or answers with an error, opens the form for the badge just as a 404 does, with a hint saying so, and Manually Enter User or a newer scan cancels the lookup in flight (`cancelLookup`), whose late answer is then ignored rather than resetting the form or putting an error over it. The by-phone check and read-back behind Register run under the same 6 seconds and the writes under `WRITE_TIMEOUT_MS` (15 seconds), which cannot leave a duplicate behind: the retry finds a record the timed-out create did make by phone number and updates it. There is no typed-ID lookup: the secondary button under Register, Manually Enter User, opens the registration form below with no badge, for an attendee without one or a badge that will not scan. No localStorage is touched and no frame leaves the page.

A badge the database does not know opens a form in place of the details: first name, last name, phone, email, company (the company box was added 2026-10-14, when the API began keeping it), and a Register button; Manually Enter User opens the same form with `pendingBadge` null and a different title and hint. `validateAttendee` trims the names and the company, normalizes the phone to bare digits (7 to 15 of them) and accepts an empty email or company; `saveAttendee` then, when there is a badge, tries `PUT /users/conf/:confNumber` first (the route the owner calls "create by confirmation number"; measured on 2026-10-09 and again on 2026-10-12 it only updates and 404s for an unknown number, but if it ever creates, the record is keyed by the badge), falls back to `PUT /users/:id` when `findUserByPhone` finds the number already there (keeping that record's balance and photo rather than making the duplicate the API would allow), and otherwise `POST /users`. `email`, `Company` (the API's spelling of the form's company box) and `confNumber` are sent every time; since 2026-10-14 the POST keeps `email` and `Company` (no read returns them, and the PUTs still drop them), while `confNumber` is dropped everywhere, so the badge ID, or "Registered manually", is written into `customAttrib`, which it keeps. The result's `byBadge` (a read by confirmation number afterwards) decides whether the page notes that a rescan of this badge will not find the record, and a `how` of `update` adds a note that the record the number already had kept neither email nor company. After the save the page continues exactly as for a known badge, with the typed email and company on screen (a known badge shows the `Company` the by-confirmation read returns) and "none, entered manually" in the Badge ID row for a manual entry. A live registration on 2026-10-12 confirmed the POST path (userId 5, later found undeletable: both DELETE routes answered 500 for it, because the owner had recorded exchanges against it and a user with an exchange row cannot be deleted, `docs/user-api.md` §3c).

Once a record with a phone number is on screen, found or just saved, Step 3 is Enroll FIDO Key: `enrollKey` in `key-enroll.js` runs the create for the bare digits with the attendee's name as `displayName`, keeps the entry in the `ishield_enrollments` list, posts it to the dev server's `/credentials` (silently absent in production), and returns warnings (non-discoverable, PIN used, credProtect not level 1, ceremony mismatch), which the page draws under the button. Only after the create does Step 4 draw the QR, from `registerUrl`: `<origin>/?userid=<digits>`, with the deployment substituted for a localhost origin and a warning that a credential written on localhost does not exist there. The phone therefore lands on the demo with the number in the box, and Enter Game's get reads it back off the key. A failed create leaves the QR hidden and explains the DOMException name with `ERROR_HINTS`. The key step has been exercised only against a stubbed `navigator.credentials.create`. The QR is drawn with the vendored `qrcode-generator` (`createSvgTag`). The exported helpers (`normalizePhone`, `formatPhone`, `registerUrl`, `attendeeName`, `cameraErrorMessage`, `lookupAttendee`, `findUserByPhone`, `validateAttendee`, `saveAttendee`) are pure or take a `fetch` so a Node harness can cover them; the module's top level only registers a `DOMContentLoaded` listener.

## Partner page (`partner.html`)

`partner.js` is page glue around a password gate, a partner strip, the open get and the balance endpoint. The page opens locked: the form checks `PARTNER_PASSWORD` (`Passkeys2026`, in plain text in the module, deliberately: a demo gate, not security), a match stores `partner_unlocked` in `localStorage` so the booth's device stays unlocked across reloads. The footer (the browser line and the Lock, Register and Login links) was removed on 2026-10-14, so a device is locked again only by clearing site data; `detectBrowser` still runs for the desktop Chrome warning. The strip at the top of the card is drawn from `PARTNERS`, one tile (icon from `partners/`, name under it) per entry, in order: RSA, Swissbit, HID, Ice Cream, Popcorn, Oxygen (Google's tile was removed and the two refreshment booths added on 2026-10-14; six tiles sit in one row on a desktop, 48px minimum each, and in two rows of three at phone width, where one row broke the names mid-word); tapping one stores it as `partner_booth` and hides the strip (since 2026-10-14: the chosen partner's icon, drawn large, and name stand in for it in `#partner-chosen`; a semi-transparent X at the top right of that header (`#change-partner`, a round button at 40% opacity; a Change link came and went earlier on 2026-10-14) clears the choice and brings the strip back; `renderBooth` draws whichever state applies), `?partner=<id>` preselects it (case-insensitive, stored, then stripped from the address bar; an unknown id is ignored), and until a partner is chosen, or when the stored id no longer exists, only the strip shows. ## Demo flow in `app.js`

Screens are LOGIN, SNA, ACTIONS, EXCHANGE and CONTACTS, chosen by `updateUI()` from `STATE.loginID`, a pending number check, and the `exchange` and `contacts` states. There is no New or Passkeys toggle and no SETUP screen since 2026-10-14 (the owner's request; before, New on ran `trustDevice()`, the phone's own iShield create then ZSM enroll, and Passkeys+ could be switched off): the device's own state picks the ceremony, Passkeys+ is always part of it, and the User ID is editable on every screen before a login. Enter Game runs `login()`. On a bound, active device that is the ZSM authenticate with Passkeys+ alone, no key and no dialog. On a device with no ZSM credential for the typed User ID but a passkey for it on the server it is the passkey alone (`bindWithPasskey`, since 2026-10-18: a private tab or another browser on a phone that has played, with no dialog, no key and no second carrier check). On a device with no ZSM credential and no passkey it is, in order: the guide dialog (`ONBOARDING_GUIDE`: "Let's get your phone ready", "We are going to do 4 things", the steps Verify your FIDO USB Key, Create a mobile device Passkey, Cryptographically bind device, Verify phone number with carrier API, and a Start button under "Start with the USB FIDO Key"); the iShield **get**, with `reconcileUserId` holding the typed User ID to the key's user handle; the second dialog (`KEY_VERIFIED_GUIDE`: "Your USB FIDO Key is now verified!" over "Now let's get your mobile device Passkey enrolled", Continue); then `bindDevice`, the ZSM + Passkeys+ enroll (one SDK call) and the number check. On a suspended device it is the get then ZSM authenticate to reactivate, with no dialog. The dialogs are the one-button `#guide-popup`, drawn by `showGuide` and settled by `hideGuide` ('ok' for the button, 'cancel' for Escape; there is no cancel button, the owner's wording, so on a phone the way out is to dismiss the key prompt). The tap on the button is also the user gesture the WebAuthn prompt that follows needs, which is why each ceremony sits directly behind one. A bound device with no passkey (a binding from before the passkey was always part of it) gets that dialog without the key line (`PASSKEY_GUIDE`) and the Passkeys+ enroll on its next Enter Game. The line under the first dialog's steps, "Start with the USB FIDO Key", is drawn as a bold centred headline (`.popup-note`), not boxed, so it does not read as a second button. Arriving via `?userid=` only fills the User ID box (the `new` parameter went with the toggle): the registration QR carries the number that was just written to a key, and Enter Game reads it back.

Every path that ends in a login passes `ensureNumberVerified(user)` before `STATE.loginID` is set: `login` after the binding enroll on an unbound device (inside `bindDevice`), after a Passkeys+-first enroll, and after the plain `authenticate`. Reactivating a suspended device skips it, and so does the passkey rebinding in `bindWithPasskey`, which carries the marker over (`carriedOver: true`) instead: the number passed the check when the phone was first bound, and the owner's rule of 2026-10-18 is not to run it again. The gate resolves at once when `sna_verified:<user>` exists. Otherwise the SNA screen comes up with the User ID formatted as a phone number (the status pills under the card are redrawn by `refreshPills` as it appears and again when the number verifies, since `updateUI` does not run until Continue), "Verify my number" runs `verifyNumber` from `sna.js` and colours its step rows as they go, a match writes the marker and shows the status "<phone> Verified" and the four indicators, labelled USB Key, Phone# Verified, Cryptographic Device Binding and Passkey Enrolled since 2026-10-13 (the first from the local marker, the second from the new one, the last two from `checkAllEnrollment`; each row reads true or false as the pills do, with unknown for a key marker this device never wrote, and both markers read through `localMarkerStates`, which answers false for a key marker that says `boundFromPasskey` and a number marker that says `carriedOver`), and Continue resolves the gate so the caller carries on into `updateUI`. There is no Cancel since 2026-10-14 (the owner's clean-up of this screen, which also dropped the sentence under the title before the check and the API line under each step): the gate resolves false only through `finishSna(false)`, which nothing calls now, though every caller still handles it by returning to the screen it came from. `updateUI` keeps the SNA screen up while the gate is pending, and `showScreen` makes the User ID read-only there; the way to a different User ID is Log Out after the check, or Reset Device. The presenter can play IDlayr's other two outcomes once with `?sna=nomatch` or `?sna=unsupported`: the value goes to `sessionStorage`, comes off the address bar, and is consumed by the next check, which then offers Try again. The stored check ID and one-time code were shown on ACTIONS in a collapsible block until 2026-10-14; now only the marker is read. The pill row reads USB Key, Phone# Verified, Device Bound (the ZSM credential), Passkey, then Passkeys+ (the labels since 2026-10-13; ids and code keep `ishield` and `number`). In a browser rebound from the passkey (`bindWithPasskey`) the first two read false, red, since 2026-10-18 (the owner's request after the private-tab test: the pills say what happened in this browser, and neither the key touch nor the carrier check did), while Device Bound and Passkey read true, because the rebind built a real ZSM share there and the passkey is the one that proved it.

ACTIONS (cleaned up 2026-10-14) opens on the balance, drawn large in `#balance-display` (a label and the points, hidden when the User ID has no record, with a brief bump animation when the number moves on screen), then four actions in two rows. Authenticate and P2P Contact Exchange are buttons that run the ZSM step-up `authenticate` first. View Contacts (since 2026-10-14, no step-up) opens the CONTACTS screen: `openContacts` re-reads the account when the login's lookup found none, reads `GET /db/users/id/:recordId/contacts` through `fetchContacts`, and `renderContactsScreen` draws the rows (`contactRow`: name, then phone, company and email) under a count line, or says the User ID has no record, there are no contacts yet, or the list could not be read; "Email me the list" is an `<a class="btn">` whose `href` is `contactsMailto(list)`, a `mailto:` with no recipient (no read returns the attendee's own email), the subject "My Authenticate 2026 contacts (N)" and one block per contact in the body, so a phone opens its mail app with it filled in; Back (`closeContacts`, then `updateUI`) and Log Out leave the screen. View Leaderboard is a plain link to the owner's `dashboard.html` on `sbit.authconcepts.com:3099`, opened in a new tab so the game session survives, with no step-up. Add Beneficiary and the old View Point Standings step-up are gone, and so are the collapsible USB Key, Passkeys+ and Silent Network Auth challenge blocks with their copy buttons (`updateChallengeDisplay`, `updateIShieldChallengeDisplay`, `updateAuthIcons` and `updateSnaDisplay` left with them; `umfa.js` still returns the challenge data, nothing draws it). P2P Contact Exchange branches to the EXCHANGE screen (below). Authenticate **earns** points: `awardPoints` re-reads the record by bare-digit phone and sends `PATCH /users/:id/balance` with the positive amount and `partner: "IDEEM"` (`CREDIT_PARTNER`, the string the API has required on every balance move since 2026-10-16), since the API adds what it is sent (until 2026-10-14 `settleAction` charged the same amount, with an overdraft check a credit does not need). The amounts are fixed per action in `ACTION_POINTS`, in points, and earned once: when the credit lands, `setAwarded` writes `points_awarded:<action>:<user>` to `localStorage`, `pointsFor` then answers 0 for that user, the button's badge (drawn by `renderActionPoints` from `updateUI` and again after a credit) goes from "+25 pts" to "0 pts", and a later press steps up and flashes "points already earned" without a PATCH. The marker is per device, like every other marker: Reset Device clears it and a second phone would earn again, since the user API has no field for it. The P2P entry in the table (100) is what an exchange earns per new contact, on both sides, but the credit is the matchmaker's, not this page's (`api/exchange.js`, since 2026-10-18; the two numbers must agree): the page only draws it on the button, where it never turns to 0 since no marker is written for it, words the outcome on the exchange screen (`exchangePointsText`), and puts the balance the completed record carries onto the ACTIONS screen (`applyExchangePoints`, a re-read when the account on hand is not this user's). A failed PATCH is re-read, never retried, because the API has no idempotency key. A missing or unreachable database never blocks the step-up itself. Every credit is formatted as points (`formatPoints`, "25 pts", up to two decimals) and the balance as whole points (`formatBalance`: `Math.floor`, "1,030 pts", no decimals since 2026-10-14), the same unit the partner booths credit; the page showed dollars until 2026-10-13.

The EXCHANGE screen serves both sides of a P2P Contact Exchange and is driven by the `exchange` object in `app.js`. The initiator's step-up is followed by a create call; the page draws the returned code as a QR of `<origin>/?exchange=<code>` with the vendored generator and polls every 2 seconds until the record has a responder or the server answers 404 (expired). The responder arrives with `?exchange=`: the code goes into `sessionStorage` under `pendingExchange`, the parameter is removed from the address bar, and `openExchangeInvite` puts the EXCHANGE screen up at once in its confirm state: the title is "Confirm sharing contact info", a status read names who is asking and says where this phone stands (since 2026-10-18: signed in today as the number shown read-only above, so confirm with the passkey; a User ID in the box but no login yet, so tap Confirm to verify; or nothing in the box, so this browser tab does not remember them, a private tab perhaps, and they enter it first; `updateUI` redraws the prompt as the box is typed in, and `renderExchange` keeps a terminal outcome in `exchange.outcome` so that redraw never loses an expired or used state), and a button of the same wording appears. An expired or already-used code is reported there and dropped. The button runs `confirmExchange`, whose passkey verification on a phone not logged in today is the demo's own `login()` (on an unbound phone the guide dialogs, the iShield touch and the ZSM enrollment, over the exchange screen; ZSM `authenticate` alone on a bound one); `login` ends in `updateUI`, which keeps the screen up, and `confirmExchange` then sends the completion itself once `STATE.loginID` is set. No page load completes an exchange (until 2026-10-18 `updateUI` did, which is why an invite could not restore the session). A phone still logged in from the day's session gets the ZSM step-up alone, as the action buttons do. Both screens then show the other person's name, phone, and User ID from the record, a line saying whether the exchange was saved to the user database (`record.upstream`, since 2026-10-14), a line saying what this side earned for the contact (`record.points`, since 2026-10-18: 100 points for a new contact with the balance after it, or why not: already a contact, the list unreadable, the row not saved, no record, or the credit refused) and, when the list is not empty, this attendee's contacts read from `GET /db/users/id/:recordId/contacts` by `renderContacts`. Done, Cancel, and Log Out all go through `endExchange`, which stops the poll and clears the pending code. `showScreen` makes the User ID read-only only once `STATE.loginID` is set, so a responder can still correct the number before confirming.

Suspension is a `localStorage` flag (`passkeys_suspended:<user>`); a suspended device requires an iShield touch plus ZSM authenticate to clear it. "Reset Device" wipes `localStorage`, `sessionStorage`, and the `ideem` IndexedDB, keeping only the username; the number-verified marker goes with them. Since 2026-10-18 the next Enter Game on that phone finds the passkey still on Ideem's server and rebinds through `bindWithPasskey`, the passkey alone with the number check carried over, so the full onboarding (guide, key, carrier check) replays only for a number with no passkey on the server. `purgeStorage` then navigates to the bare page path, dropping a `?userid=` the reload would otherwise read again, and the page comes back on LOGIN with the User ID editable, as it is on every screen before a login since the toggles went (a `justReset` marker that switched New back on lived for part of 2026-10-14).

A login lasts 36 hours (the owner's rule: a day from 2026-10-14, 36 hours since 2026-10-18): `updateUI` writes `session` (`{ user, at }`) to `localStorage` the first time it sees `STATE.loginID` for a User ID, and `restoreSession` on page load sets `STATE.loginID` again when that marker is under `SESSION_TTL_MS` (36 hours) old, names the User ID in the box, the device is not suspended and `checkAllEnrollment` still reports the ZSM credential (a device that lost it drops the marker); the page then opens on ACTIONS with no ceremony, and the step-up actions work as usual. The timestamp is the login's and a return does not refresh it. Log Out clears the marker and Reset Device wipes it with the rest. A page opened from a P2P invite (`?exchange=`) restores it like any other load since 2026-10-18 (before, it never did, so a responder logged in that day met an editable User ID box and a page that looked logged out): the confirm is still a verification, the ZSM step-up, and a load never completes an exchange by itself.

The User ID input carries deliberate password-manager opt-outs (`name="ishield-user-id"`, `data-1p-ignore`, etc.) because iOS AutoFill was offering saved `*.vercel.app` logins over it. Keep them if the field is restyled.
