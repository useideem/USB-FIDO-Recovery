# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

This repository, `USB-FIDO-Recovery` (`useideem/USB-FIDO-Recovery` on GitHub, `~/GitHub/USB-FIDO-Recovery` locally), is a USB FIDO key recovery demo: a static, no-bundler browser app that binds three factors to a phone, the phone number checked by a simulated carrier call, an Ideem ZSM / Passkeys+ passkey, and a Swissbit iShield USB key that the phone itself encodes with raw WebAuthn (the user creates the key's PIN as it is written), and that recovers from a lost key by encoding a blank replacement. It was cloned on 2026-10-21 from `useideem/authenticate26` at its commit e0ea19e, the Authenticate 2026 conference demo, with the full history, and rebuilt the same day to the customer's brief. Everything conference-shaped went with that rebuild: the partner booths, the landing page and party theme, the points, the P2P contact exchange, the user-database proxy and the exchange function, the badge scanner. The history before 2026-10-21 is the conference demo's and `git show e0ea19e:CLAUDE.md` describes it. The original repository and its deployment are untouched by work here.

Plain ES modules served as-is; there is no framework, no transpiler, and no linter configured. Everything a user reads calls the hardware a **FIDO key** or **USB key**; file names, identifiers and storage keys keep `ishield`. `.gitignore` excludes `tests/`, `test-results/`, and `playwright.config.js`, so tests are local-only and not part of the repo.

Three pages share `style.css` and a handful of modules:

| Page | Role |
|---|---|
| `index.html` + `app.js` | The main page: User ID (the phone number), one **Continue** button, and three screens. A phone that holds no ZSM share for the number is set up: the guide dialog, the SNA check, the passkey, then the create that encodes the blank key (the browser has the user create the key's PIN). A phone that holds one signs in on the passkey alone. HOME shows the key this phone encoded and when, the four factor rows, the challenge blocks, and the buttons Authenticate, Verify USB key, I lost this key, Encode new FIDO key, Log Out. Reset Device in the footer |
| `register.html` + `register.js` | A bench tool, outside the user's flow since 2026-10-31: a phone number box and **Enroll Key**, which writes the number onto the inserted key from a desktop browser with the same create (`key-enroll.js`), then a QR code and a link that open the main page with `?userid=<digits>`. A key written here is read on HOME with Verify USB key |
| `fido-test.html` + `fido-test.js` | Raw WebAuthn tester for hardware keys, no SDK involved. Nothing links to it; open it by URL. It is the measurement tool for the open questions below |

## The customer's flow (2026-10-31, superseding the 2026-10-21 brief where they differ)

The story: a bank ships the user a blank FIDO USB key. On their phone the user binds the number and the phone, then encodes the key themselves, creating its PIN. When the key is lost they say so in the app, the old key is refused, the bank ships another blank key, and after the passkey the user encodes that one.

- First use: the key arrives blank. The main page runs the SNA check, enrolls the passkey, then runs the WebAuthn create that writes the verified number onto the key. Until 2026-10-21's brief was superseded, the registration page wrote the key and the main page only read it; now the main page writes it, at setup and in recovery.
- The PIN is the FIDO key's own PIN, stored on the key, not an app code. The create requires user verification (UV true), so on a blank key the browser has the user create the PIN before the touch, and asks for it on every ceremony afterwards, on every device. The key enforces the PIN rules: the iShield advertises a four-character minimum and, as Swissbit documents for every applet on the iShield Key 2, refuses a run such as 1234 or 123456 and a character repeated four times (found 2026-11-01, when Safari's "Set Up Security Key" sheet answered "Unrecognized PIN code" to a PIN the key refused). The guides and the encode flash say so before the sheet opens. The page cannot set, read or size the PIN, and there is no in-app PIN form.
- Sign-in after setup is the passkey alone.
- HOME shows the USB key with the date and time it was encoded in this app, on this phone.
- "I lost this key" opens a dialog saying the bank would be notified and would send a blank replacement. Once lost, that key is no longer used.
- "Encode new FIDO key" demands the passkey again, then encodes the blank replacement with the same phone number; the new credential has its own key pair. The previous key is refused from then on, by the app and, through `excludeCredentials`, by the key itself. The SNA check is not repeated in recovery.
- The challenge each factor's ceremony produced stays on HOME, with the signed challenge where the ceremony signs one (the passkey, and the key on Verify USB key) and the public key for the create.
- There is no backend. Everything the app knows about a user's keys lives in the phone's browser; a second phone has its own records.

## Commands

```sh
npm install              # postinstall runs `npm run build`
npm run build            # node build.js -- copies the SDK + qrcode-generator from node_modules into vendor/
node dev-server.mjs      # http://localhost:8080 (PORT=3000 to change)
./run.sh                 # bare python http.server fallback
node tests/key-records.test.mjs   # the Node harness (tests/ is git-ignored; see Testing)
```

`vendor/` is git-ignored and must exist before any page loads: `index.html` resolves `@ideem/zsm-client-sdk` through an import map to `./vendor/@ideem/zsm-client-sdk/ZSMClientSDK.js`, and `register.js` dynamically imports `./vendor/qrcode-generator/dist/qrcode.mjs`. If a page 404s on an import, run the build. Adding a new npm dependency that a page imports means adding it to the `packages` list in `build.js` as well. The SDK is pinned to `latest` in `package.json`; the vendored copy is 2.9.3.

`dev-server.mjs` serves the directory and keeps two dev-only endpoints for the key tester and the registration page: `POST /log` (appends to `.dev-logs/fido-test.jsonl`) and `GET/POST /credentials` (a shared list in `.dev-logs/credentials.json`). Both are silently absent in production. It proxies nothing: the app has no backend of its own. Listening on a local port is blocked in Claude Code's sandbox (EPERM on listen); run it unsandboxed, or set `sandbox.network.allowLocalBinding: true`.

Testing on a phone needs HTTPS. A Cloudflare quick tunnel works; the hostname changes every run, so credentials made under it are bound to that hostname only:

```sh
cloudflared tunnel --no-autoupdate --url http://localhost:8080
```

## Module layering

```
app.js / register.js / fido-test.js       page glue, DOM, screens, dialogs, flash messages
   |         |              |
   +---------+---- key-enroll.js   the discoverable create that encodes a key: app.js at setup and recovery, register.js as a bench tool
   |         |          |     |
   |         +---- webauthn-util.js <-+     CBOR decoder, authenticator-data parser, RP-side checks
   |                     |
   +---- umfa.js         |                  Ideem UMFAClient wrapper; the only module that imports the SDK
   |        |            |
   +---- ishield.js <----+                  the raw WebAuthn get; zero SDK deps; also base64url + SHA-256 helpers
   |
   +---- key-records.js                     the keys a browser has encoded or read, lost, replaced, and when; no DOM
   |
   +---- sna.js                             simulated Silent Network Authentication; no DOM, no network, no SDK
```

- `ishield.js`, `umfa.js`, `key-records.js` and `sna.js` are the partner-facing integration code and never touch the DOM. Keep UI concerns in the page scripts.
- `ishield.js` holds one ceremony, `webauthnIdentify({ userVerification, allowIds })`: the get (`allowCredentials` from `allowListFor(allowIds)`, each id on `transports: ['usb', 'nfc']`, deduplicated and capped at Chrome's 64, which sends the browser straight to its security-key sheet; an empty list, the open get, when the page passes no ids; `userVerification: 'required'`; `hints: ['security-key']`, advisory, honoured by Chrome 128+ and ignored by Safari) that returns `credentialId`, `authenticatedUser` (the user handle as text), the challenge sent, `clientDataHash`, `signatureHex`, the `userPresent` and `userVerified` flags and the `signCount`, read from the assertion's authenticator data inline so the module keeps zero imports. `webauthnAuthenticate(user, { allowIds })` wraps it with the expected user and logs a mismatch; the page decides. The non-discoverable create and the suspension helpers the conference demo had are gone.
- `key-enroll.js` holds the create. `createOptions`: `residentKey: 'required'`, `userVerification: 'required'`, `authenticatorAttachment: 'cross-platform'`, `hints: ['security-key']`, `attestation: 'none'`, `extensions: { credProps: true }` and no credProtect extension (with verification on every get the level decides nothing). `user.id` is the phone number as UTF-8. `enrollKey({ phone, displayName, excludeIds })` runs it, excludes `excludeIdsFor(phone, excludeIds)`: the credentials already in the `localStorage` list `ishield_enrollments` for that number plus the ids the caller passes (the main page passes every record in `key-records.js`, so a lost key that turns up is refused by the key with `InvalidStateError`), stores the entry (id, public key when the browser exposes it, algorithm, `rk`, `uvAtCreate`, sign count, the challenge, the time), and returns `warnings`: a non-discoverable credential, a create whose UV flag is false (no PIN protects it), or a ceremony check that did not match. `detectBrowser` names the browser from UA Client Hints or the user agent string.
- `key-records.js` is the per-browser memory of a user's keys, `localStorage` `ishield_keys:<user>`, newest first: `{ id, userHandle, status: 'active' | 'lost' | 'replaced', associatedAt, encodedAt, lastVerifiedAt, lostAt, replacedAt, userVerified, signCount, publicKey, alg }`. `encodedAt`, `publicKey` and `alg` are set when the record came from the create on this phone (`associateKey` with `encoded: true`) and null for a key only read. At most one record is active. `recordVerification(user, assertion, now)` is a get (Verify USB key on HOME): `'associated'` when the browser had no active key, `'verified'` for the active key (its `lastVerifiedAt` moves), `'refused'` for a lost or replaced key, `'unknown'` for a different key while one is active (nothing changes; Encode new FIDO key is the way to swap). `associateKey(user, assertion, now)` is the create at setup and in recovery: `'associated'` makes the id the active key and marks the previous one `replaced`, `'same'` leaves the active key as it is, `'refused'` is a lost or replaced key. `markLost(user, now)` marks the active key lost. `refusedKey(user, id)` answers for a lost or replaced id. `now` is a parameter so the Node harness can cover it.
- `sna.js` is a simulation of IDlayr's Secure SNA flow (`https://secure-sna-demo.idlayr.com`). `verifyNumber(phone, { scenario, onStep, speed, signal })` plays six timed steps and resolves to `{ match, checkId, code, reason, verifiedAt, steps }` without any network request; the scenarios are `success`, `nomatch` and `unsupported`. `isNumberVerified` / `setNumberVerified` / `getNumberVerification` keep a per-device marker, `sna_verified:<user>` in `localStorage`, that a successful check writes. A real integration replaces the inside of `verifyNumber` with calls to a backend holding the IDlayr key; nothing in `app.js` changes.
- `umfa.js` loads `zsm_app_config.json` at module init and caches one `UMFAClient` per `consumer_id`. `initializeZSMClient(user)` must precede `checkAllEnrollment`, `enroll`, and `authenticate`; `resetClient()` on logout. `enroll` and `authenticate` take the SDK's mode as their second argument (`true` is `'preferred'`, `false` is `'prevented'`, the strings pass through) and call `validateToken` automatically; an enrollment is not activated until that POST succeeds. The page passes `'required'` everywhere: in `'preferred'` mode a cancelled passkey sheet falls back to a ZSM-only ceremony with no passkey, and the passkey is this demo's recovery factor. In `'required'` mode the SDK's `enroll` on a browser with no share whose user already has a passkey on the server authenticates that passkey and rebuilds the share rather than registering a second one (its `addZSMToPasskeyCredential` path), which is what a phone after Reset Device, or a second browser, gets. `challengeDataFrom(credential)` is the challenge and signed challenge the HOME blocks show, from an `enroll` or `authenticate` result alike.
- `state.js` is a classic (non-module) script exposing a global `State` Proxy. The demo only uses `STATE.loginID` and `STATE.reset()`.

## WebAuthn constraints

The measurements behind these are in `docs/ishield-pinless-discoverable.md`, whose sections 1 to 6 are the September 2026 PIN-less findings and whose section 7 is the PIN change.

- **The keys carry a PIN, and the user creates it on the phone** (the customer's rule, 2026-10-21, and flow, 2026-10-31). The create requires user verification (UV true), so on a blank key the browser has the user create the PIN before the touch and asks for it on every ceremony afterwards, on every device. The key enforces the PIN rules. The get requires verification too, and the UV flag either ceremony returns is shown on HOME as "PIN verified". The page cannot set, read or size the PIN, and there is no in-app PIN form.
- **Measured on 2026-11-01, in Safari on a Mac (macOS 26.5)**: the create on the blank iShield from the main page, with the PIN created in Safari's own "Set Up Security Key" sheet. It works once the PIN meets the key's rules; the sheet says "Unrecognized PIN code. Please try again." to one that does not, and nothing is consumed, since a key with no PIN has no retry counter. Desktop Chrome's September `0x37` on PIN setup was the same refusal (CTAP `PIN_POLICY_VIOLATION`), not a Chrome bug, and has not been retried with a PIN the key accepts.
- **Not yet measured, and gating the first phone walkthrough**: the create from an iPhone and an Android, the PIN prompt on a later get, and the allow-listed get on Verify USB key (that it opens the security-key sheet and that the user handle comes back). Run them with `fido-test.html` on the deployed origin, Create set to Discoverable and User verification Required. Pre-setting the PIN with `fido2-token -S` skips the step the customer asked for, so it is the fallback only if a phone browser cannot set one. `fido2-token -R` returns a demo key to blank. The measurement doc's section 8 has the detail.
- **Verify USB key names the phone's keys.** `verifyUsbKey` passes every record's id (active, lost and replaced) as `allowIds`, so the browser opens its security-key sheet rather than the passkey chooser that put the device biometric and the Ideem passkey first on the empty-list get (seen in Safari on the Mac, 2026-11-01; `hints` alone did not prevent it, since Safari ignores hints). A lost key is listed so that it still signs and the refusal is the app's, with its date. With no records the get is open, which is how a second phone adopts a key. If an allow-listed get returns no user handle, `verifyUsbKey` falls back to the handle recorded for the matched credential before `sameUser`.
- **Encode on the production origin.** Credentials are bound to the RP ID (hostname). A key encoded on localhost or a tunnel holds nothing the Vercel site can read, and vice versa. The registration page's QR code points at `location.origin`, except from localhost, where it points at `PUBLIC_DEMO_ORIGIN` and the page says the credential just written will not be found there.
- **Phone numbers are bare digits everywhere**: on the key as `user.id`, in the `?userid=` parameter, in the records. `normalizePhone` (`register.js`) and `phoneDigits` (`app.js`) apply the same rule: strip non-digits, drop a leading US `1` from an 11-digit number. Format for display only. The create writes the User ID as typed, after SNA verified it.
- **The key is the authority on identity.** After a successful get (Verify USB key), `sameUser` in `app.js` compares the signed-in User ID with the user handle the key returned (or, when an allow-listed get returned none, the handle recorded for that credential); a different number, or no handle, stops with `keyMismatchMessage`. Nothing rewrites the box, since the user is logged in.
- **Every ceremony sits directly behind a tap.** The guide dialogs exist so that the tap on their button is the user gesture the WebAuthn prompt that follows needs: the passkey after the number check, the create after the passkey (at setup and in recovery). The browser's own PIN-creation sheet follows that tap.
- **A platform passkey answering the key prompt is a stop.** `webauthnIdentify` refuses an assertion whose `authenticatorAttachment` is `platform` and the page says a password manager may be stepping in front of the security-key prompt. There is no "continue without the key" path.

## Registration page (`register.html`)

A bench tool since 2026-10-31: the user's flow never visits it, because the main page encodes blank keys on the phone. It remains the way to write a key from a desktop browser, for the get path (Verify USB key on HOME adopts a key when the phone has none active) and for the key tester. `register.js` is page glue with no SDK or WebAuthn involvement beyond `enrollKey`. Enroll Key validates the box (`validatePhone`: bare digits, 7 to 15 of them), writes the digits back into it, runs `enrollKey({ phone, displayName })` with the formatted number as the display name, draws the warnings under the button, posts the entry to the dev server's `/credentials` (absent in production), shows what the key did (User ID, the credential id shortened, "PIN verified" yes/no from the UV flag, the time) and then the QR code from `registerUrl`: `<origin>/?userid=<digits>`, with the deployment substituted for a localhost origin and a warning that a credential written on localhost does not exist there. A failed create explains the DOMException name with `ERROR_HINTS`. The footer names the browser, with a word for desktop Chrome. The exported helpers (`normalizePhone`, `formatPhone`, `validatePhone`, `registerUrl`, `shortId`, `PUBLIC_DEMO_ORIGIN`) are pure, so the Node harness covers them; the module's top level only registers a `DOMContentLoaded` listener. The page uses the plain theme (`style.css` only, the `.rg-` classes at its end), as the key tester does.

## Demo flow in `app.js`

Screens are LOGIN, SNA and HOME, chosen by `updateUI()` from a pending number check first, then `STATE.loginID`. The User ID box is editable on LOGIN and read-only on SNA and HOME. Under Continue a hint says whether this phone will be set up or just ask for the passkey (`renderLoginHint`, from `factorStates`).

**Continue** runs `login()`. The device's own state picks the ceremony, from `checkAllEnrollment`'s `hasZSMCred`:

- A phone that holds a ZSM share for the number: `verifyPasskey` (`authenticate(user, 'required')`), then `ensureNumberVerified` without force (a phone that holds the SNA marker answers at once), then `STATE.loginID` and HOME.
- A phone that holds none: `ONBOARDING_GUIDE` ("Let's get your phone ready.", the three steps, "Start with your phone number", Start), then `ensureNumberVerified(user, { force: true })`, the SNA screen, always at setup; then `PASSKEY_GUIDE` ("Your number is verified!", Continue), whose tap is the gesture for `enroll(user, 'required')`; then `STATE.loginID` and `updateUI()`, so HOME is behind the last dialog; then `ENCODE_KEY_GUIDE` ("Insert the FIDO USB Key from your bank", "Encode the key"), whose tap is the gesture for `encodeKey(user, 'encode')`. A cancelled key dialog leaves the phone bound, on HOME, with the flash saying to encode the key from there. A cancelled earlier dialog or a failed step returns to LOGIN with a flash.

**`encodeKey(user, purpose)`** is the create, shared by setup (`'encode'`) and recovery (`'replace'`): `enrollKey({ phone: user, displayName, excludeIds: every record's id })`, then `associateKey` with `keyFromEnrollment` (`encoded: true`, the public key and algorithm). The flash while it runs says to create a PIN for the key when the phone asks, then touch it. A thrown `InvalidStateError` is the key refusing an excluded credential (`encodeFailureMessage`: the key is already encoded for this number on this phone, a lost or replaced key stays refused); `NotAllowedError` is a cancel, a timeout or no PIN. The result goes to the USB Key block through `encodeResultFrom`; `warnings` from the create (a non-discoverable credential, UV false) are flashed as a failure while the record still stands.

**The SNA screen** is the conference demo's: "Verify my number" runs `verifyNumber` from `sna.js` and colours its step rows as they go, a match writes the marker, puts the check id and code into the SNA result, and shows "<phone> Verified" and the four indicators (`renderFactors('sna-ind', …)`); Continue resolves the gate. The presenter can play IDlayr's other two outcomes once with `?sna=nomatch` or `?sna=unsupported`: the value goes to `sessionStorage`, comes off the address bar, and is consumed by the next check, which then offers Try again. There is no Cancel.

**HOME** (`renderHome`): the key card (`renderKeyCard`: the newest record's credential id shortened with the full id as a tooltip, Encoded (or Associated, for a key this phone only read) and Last verified as date and time to the second in the phone's locale via `formatWhen`, Status as Active, "Reported lost <when>" or "Replaced <when>"; the records before it as a history list; "No FIDO key is associated on this phone." when the list is empty), the four factor rows (`factorStates`: USB Key from `activeKey`, Phone# Verified from the SNA marker, Cryptographic Device Binding from `hasZSMCred`, Passkey Enrolled from `hasRemotePasskey` or `hasLocalPasskey`), the three challenge blocks, and the buttons.

**The challenge blocks** are the conference demo's terminal-style `details` rows, restored from the commit before its 2026-10-14 clean-up, with the rows cloned from the `#challenge-row-template` by `renderChallengeBlock` and a meta line under each. What each factor's last ceremony produced is kept per User ID in `sessionStorage` `factor_results:<user>` (`setResult` / `loadResults`), so a reload within the tab keeps it, and Log Out clears it. USB Key after a create (`purpose` `'encode'` or `'replace'`): Challenge (what was sent, base64url), Public key (SPKI, base64url, when the browser exposed it), Credential; meta "Key encoded" or "Replacement key encoded", "PIN verified" or "PIN not verified", the algorithm name, the sign count, the time. USB Key after a get (`'verify'`): Challenge, Client data hash, Signed challenge (the signature, hex), Credential; meta "Key verified", the PIN flag, the sign count, the time. Passkey: Challenge and Signed challenge from `challengeDataFrom`; meta Enrollment or Authentication and the time. Silent Network Auth: Check ID and Code; meta the number and the time, falling back to the marker when the tab has no result of its own. The copy buttons are wired by delegation on the document. No signature is verified on HOME yet; the phone now holds the public key of a key it encoded (`publicKey` in the record), so a get's signature could be checked locally as a follow-up.

**Authenticate** is `verifyPasskey` again, drawn into the Passkey block. **Verify USB key** is `verifyUsbKey`: the get straight from the tap, with every recorded id in `allowCredentials` (the open get when there are none), `sameUser` on the handle (the record's handle when the get returned none), then `recordVerification`: the active key moves its Last verified and the result is drawn as "Key verified"; a lost or replaced key flashes when it was lost, which is how the demo shows the old key disabled; a different key while one is active flashes and points at Encode new FIDO key; with no active key the key read becomes the associated one (a second phone adopting a key it did not encode). **I lost this key** opens `LOST_KEY_GUIDE` ("Report this FIDO key lost", the note about the bank and a blank replacement, "Report it lost" with "Keep it" as the second button); the report runs `markLost`, the card shows the key as lost, the USB Key factor reads false, and the button is disabled while no key is active. **Encode new FIDO key** opens `ENCODE_NEW_GUIDE` (two steps, "Start with the Passkey"), then `verifyPasskey`, then `NEW_KEY_GUIDE` ("Insert the new FIDO USB Key", "Encode the key"), whose tap is the gesture for `encodeKey(user, 'replace')`: the new credential becomes the associated key with its time, the previous key marked replaced, the result in the USB Key block as "Replacement key encoded". There is no SNA repeat in recovery. Every path ends in `updateUI`.

**Log Out** clears the tab's results, resets the SDK client and `STATE`, and returns to LOGIN; the key records and the markers stay. There is no session restore: every page load starts on LOGIN and Continue signs in again (the conference demo's 36-hour session was dropped on 2026-10-21 so the ceremonies are always seen). **Reset Device** (`purgeStorage`) wipes `localStorage`, `sessionStorage` and the `ideem` IndexedDB, keeping only the username, and navigates to the bare page path, dropping a `?userid=`; the next Continue sets the phone up again: the passkey step authenticates the passkey the server still knows, and the key step encodes whatever key is inserted afresh (a key already holding a credential for this number replaces it, since nothing on the phone excludes it any more).

Arriving via `?userid=` only fills the User ID box: the registration page's QR carries the number that was just written to a key. The User ID input carries deliberate password-manager opt-outs (`name="ishield-user-id"`, `data-1p-ignore`, etc.) because iOS AutoFill was offering saved `*.vercel.app` logins over it. Keep them if the field is restyled.

## Testing

`tests/key-records.test.mjs` is a Node harness for the pure modules: `key-records.js` end to end (associate, verify, unknown, lost, refused, replace, same, a second user, clear, and the create path: `encodedAt`, the public key and algorithm, a get keeping them, the lost key refused and the replacement encoded), `key-enroll.js`'s pure parts (`excludeIdsFor` merging the enrollment list with the caller's ids, `createOptions`), `ishield.js`'s `allowListFor` (the usb/nfc entries, deduplication, the cap of 64, empty for none) and `webauthnIdentify` against a stubbed `navigator.credentials.get` (the allow list, the hint, required verification, the open get with no ids), and the registration page's helpers, with `localStorage` and `document` stubbed. `tests/` is git-ignored, so it is local to this machine; recreate it from this description if it is missing.

On 2026-10-21 both pages were driven in Chrome on localhost with `navigator.credentials` stubbed and the SDK's `UMFAClientBase.prototype` methods replaced (the exported `UMFAClient` is a wrapper whose constructor returns the plugin-managed class, so a stub has to go on the base prototype before the client for a new User ID is created).
