# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, no-bundler browser demo for the Authenticate 2026 conference: Swissbit iShield USB keys (raw WebAuthn) combined with Ideem's ZSM / Passkeys+ SDK. Plain ES modules served as-is; there is no framework, no transpiler, and no linter configured. Everything an attendee reads calls the hardware a **FIDO key**, never an iShield key (the owner's request, 2026-10-13); file names, identifiers and storage keys keep `ishield`. On the demo page the status pill, the SNA indicator and the challenge section label go further and say **USB Key**, and the number pill and indicator say **Phone# Verified** (2026-10-13). `.gitignore` excludes `tests/`, `test-results/`, and `playwright.config.js`, so any Playwright tests are local-only and not part of the repo.

Four pages share `style.css` and a handful of modules:

| Page | Role |
|---|---|
| `index.html` + `app.js` | The demo: Trust Device and Login (both buttons read **Enter Game** since 2026-10-13; a suspended device reads "Reactivate & Enter Game"), step-up actions, suspend/reactivate. Dressed in the party theme (`party.css` after `style.css`, `body.party`): top bar, the five-logo sponsor strip, the entry photo behind a translucent card |
| `register.html` + `register.js` | Registration page, in the party theme since 2026-10-13 (top bar, five-logo strip, translucent card; footer links Login and Partner booth): Register opens the laptop camera, decodes the badge QR (a confirmation number), looks the attendee up at `/db/users/conf/:confNumber` (or takes name, phone and email from a form when the badge is unknown or there is none), writes the number onto an iShield key (`key-enroll.js`), then shows a QR that opens the demo with `?userid=<digits>` so the phone lands on Login. It replaced the booth page `enroll.html` on 2026-10-12; that URL now redirects here |
| `partner.html` + `partner.js` | Partner booth, in the party theme since 2026-10-13: a hard-coded password unlocks it, a strip of partner tiles (Google, RSA, Swissbit, HID, Ice Cream) picks the booth, Identify runs the open get (`webauthnIdentify` in `ishield.js`), takes the phone number off the key's user handle, shows that user's account in points and moves its balance with the partner's preset buttons and two Custom buttons through `PATCH /users/:id/balance` |
| `fido-test.html` + `fido-test.js` | Raw WebAuthn tester for hardware keys, no SDK involved. No page links to it since 2026-10-13 (the Key tester footer links were removed); open it by URL |

A fifth page stands apart: `landing.html` is the conference landing page, a dark "Death to Passwords" party theme copied from the API owner's welcome page at `sbit.authconcepts.com:3099/index.html` (added 2026-10-13). It has no script and does not load `style.css`. The theme lives in `party.css`, scoped to `body.party`: the entry photo as the page background, the dark top bar, the white sponsor strip, cream text, and (for a page that also loads `style.css`) a translucent card with a gold edge and a `.page` wrapper that takes over the demo's centred column; `index.html`, `register.html` and `partner.html` load it after `style.css` for the same look. `landing.css` holds only the landing page's hero (eyebrow, neon sign, intro, the two links) and the games panel. The images are in `landing/` (the entry photo downscaled to 1920 px as JPEG, the neon sign at 1280 px, the FIDO Alliance logo), and the sponsor strips reuse the logos in `partners/` (plus `ideem-logo.png` on the demo and registration pages). The landing page carries exactly two links: Login goes to `index.html`, Leader Board goes to the owner's `dashboard.html` on that host, which lists every user in the same database by balance (shown there as dollars). The Games panel under the hero is placeholder copy until the owner supplies the text on the games and how to play.

## Commands

```sh
npm install              # postinstall runs `npm run build`
npm run build            # node build.js -- copies SDK + qrcode-generator + jsqr from node_modules into vendor/
node dev-server.mjs      # http://localhost:8080 (PORT=3000 to change)
./run.sh                 # bare python http.server fallback; no /db proxy, no /log
```

`vendor/` is git-ignored and must exist before any page loads: `index.html` resolves `@ideem/zsm-client-sdk` through an import map to `./vendor/@ideem/zsm-client-sdk/ZSMClientSDK.js`, `app.js` and `register.js` dynamically import `./vendor/qrcode-generator/dist/qrcode.mjs`, and `register.html` loads `./vendor/jsqr/dist/jsQR.js` as a classic script (a UMD bundle that sets `window.jsQR`; `register.js` reads the global). If a page 404s on an import, run the build. Adding a new npm dependency that a page imports means adding it to the `packages` list in `build.js` as well.

Use `dev-server.mjs`, not `run.sh`, for anything touching the user database or the P2P exchange: only the Node server proxies `/db/*` and mounts `/api/exchange`. It also accepts `POST /log` (appends to `.dev-logs/fido-test.jsonl`) and `GET/POST /credentials` (shared list in `.dev-logs/credentials.json`); both are dev-only and silently absent in production.

Testing on a phone needs HTTPS. A Cloudflare quick tunnel works; the hostname changes every run, so credentials made under it are bound to that hostname only:

```sh
cloudflared tunnel --no-autoupdate --url http://localhost:8080
```

## Vercel deployment

Production is `https://authenticate26.vercel.app`, deployed from GitHub (`useideem/authenticate26`, branch `main`). There is no `.vercel/` link in this checkout and no Vercel CLI installed; push to deploy. `vercel.json` sets `outputDirectory` to `.`, so the whole repo root is the static site, including `api/db.js` source and `zsm_app_config.json`.

There are two serverless functions. `api/db.js` is a proxy to the Ideem user API at `https://sbit.authconcepts.com:3033/api` (override with the `DB_API` env var). The rewrite in `vercel.json` maps `/db/:path*` to `/api/db?path=:path*`. Two constraints were measured on real deployments and must be kept:

- **Flat file, path in the query.** A catch-all `api/db/[...path].js` matched only one path segment on Vercel (`/api/db/users` worked, `/api/db/users/9999` returned Vercel's NOT_FOUND). Keep the function at `api/db.js` with nothing dynamic in its name and pass the remainder as `?path=`.
- **A function, not a plain external rewrite.** Vercel does not document non-standard ports (`:3033`) in rewrite destinations. A server-side fetch has no such ambiguity.

`dev-server.mjs` implements the identical proxy in `handleDb`, so pages always fetch the relative path `./db/...` and work unchanged on localhost, a tunnel, and Vercel. Change the two together. The same goes for the redirect from `/enroll.html`, the booth page retired on 2026-10-12, to `/register.html`: `vercel.json` answers it with a 307 and the dispatch in `dev-server.mjs` does the same.

The second function is `api/exchange.js`, the P2P Contact Exchange matchmaker, reached at `/api/exchange` with no rewrite. It is one flat file for the same reason as the proxy, dispatching on method and the `?code=` query: `POST` without a code creates an exchange for `{ userId }`, `GET ?code=` is what the initiator's page polls, `POST ?code=` completes it for the responder's `{ userId }`, and a bare `GET` is a health check. It answers 404 for a code it does not hold (never issued or expired) and 409 when the code was already completed, and the page branches on exactly those two. Contact fields are read from the user API by bare-digit phone, never taken from the browser; a User ID with no record still exchanges, with `found: false`. Records expire after `EXCHANGE_TTL_SECONDS` (default 600). The store is Redis through Upstash's REST API when `KV_REST_API_URL` and `KV_REST_API_TOKEN` (the Vercel Marketplace names) or `UPSTASH_REDIS_REST_URL` and `_TOKEN` are set, with or without the `PREFIX_` a Custom Prefix on the Vercel connection adds, otherwise a process-local Map. The health check at `/api/exchange` reports `store`, the variable that supplied the Redis URL, and the names (never values) of every Redis-looking variable the deployment can see; open it first whenever the page shows the memory-store warning on Vercel. The Map is correct on `dev-server.mjs`, which imports the function and mounts it at the same path, but on Vercel it is only a fallback: the initiator's poll and the responder's completion can reach different instances, so every response carries `store` and the page shows a warning when it reads `memory` off localhost. Add Upstash Redis to the Vercel project for the real thing. The ZSM token is deliberately never sent to this function: the SDK's validate-token window is a few seconds and the call stays inside `umfa.js`, so the function trusts the User ID it is given.

The upstream API has no authentication and no CORS headers. Its measured behaviours (exact-string phone matching, PUT replaces rather than merges, duplicate phones allowed, PATCH balance is an additive ledger adjustment that permits overdrafts) are in `docs/user-api.md`. Read it before touching any `/db` call. The full route list is the owner's Postman export at `docs/IdeemAPI.postman_collection.json`; it names the 15 routes but has no responses or PUT bodies, so the markdown doc is the behavioural reference and the collection is only the map.

Users are keyed two ways: phone number and badge confirmation number (`/users/conf/:confNumber`). The confirmation-number routes are case-insensitive, the lookup returns an object rather than an array, and only that route and the write-response bodies carry the `confNumber`, `Company`, and `email` fields; list, by-id, and by-phone reads omit them. No write route stores those three fields, so the API cannot assign a confirmation number: the PUT by confirmation number only updates a record that already has one and 404s otherwise, despite the collection calling it "Create". The balance PATCH by confirmation number is the same additive ledger adjustment as the other balance routes. The owner's test user `KVNLHY66K2P` must never be replaced or deleted.

## Module layering

```
app.js / fido-test.js / register.js      page glue, DOM, screens, flash messages
   |           |              |
   |           |              +---- key-enroll.js   the discoverable create that writes a key, as a function
   |           |                        |      |
   |           +---- webauthn-util.js <-+      |     CBOR decoder, authenticator-data parser, RP-side checks
   |                         |                 |
   +---- umfa.js             |                 |     Ideem UMFAClient wrapper; the only module that imports the SDK
   |        |                |                 |
   +---- ishield.js <--------+-----------------+     raw WebAuthn for the key; zero SDK deps; also base64url + SHA-256 helpers
   |
   +---- sna.js                          simulated Silent Network Authentication; no DOM, no network, no SDK

partner.js ---- ishield.js (webauthnIdentify) and key-enroll.js (detectBrowser only)      the partner page; talks to /db itself
```

- `ishield.js` and `umfa.js` are the partner-facing integration code and never touch the DOM. Keep UI concerns in the page scripts.
- `sna.js` is a simulation of IDlayr's Secure SNA flow (`https://secure-sna-demo.idlayr.com`), with the same no-DOM rule. `verifyNumber(phone, { scenario, onStep, speed, signal })` plays six timed steps and resolves to `{ match, checkId, code, reason, verifiedAt, steps }` without any network request; the scenarios are `success`, `nomatch` (fails on the PATCH with `match: false`) and `unsupported` (stops at the network step). The step wording is `SNA_STEPS` and the page draws its list from it. `isNumberVerified` / `setNumberVerified` / `getNumberVerification` keep a per-device marker, `sna_verified:<user>` in `localStorage`, that only a successful check writes. A real integration replaces the inside of `verifyNumber` with calls to a backend holding the IDlayr key; nothing in `app.js` changes.
- `umfa.js` loads `zsm_app_config.json` at module init and caches one `UMFAClient` per `consumer_id`. `initializeZSMClient(user)` must precede `checkAllEnrollment`, `enroll`, and `authenticate`; `resetClient()` on logout. `enroll` and `authenticate` call `validateToken` automatically, and an enrollment is not activated until that POST succeeds.
- On any `localhost:<port>` origin, `umfa.js` zeroes every hex segment of the config and sets `application_environment` to `TEST`, so the SDK initialises without real credentials. Any other origin (tunnel, Vercel) uses the real values in `zsm_app_config.json`.
- `state.js` is a classic (non-module) script exposing a global `State` Proxy. The demo only uses `STATE.loginID` and `STATE.reset()`; the `stateChange` events it dispatches are unused.
- The README's quick-start still shows a `@ideem/plugins.passkeys-plus` side-effect import. That package was removed; `umfa.js` imports only `UMFAClient` from `@ideem/zsm-client-sdk`, and the SDK is pinned to `latest` in `package.json`.

## WebAuthn constraints that are not negotiable

These came out of two days of measurement on real keys and browsers (`docs/ishield-pinless-discoverable.md`). Breaking any of them breaks retrieval on attendees' phones.

- **Demo keys must stay PIN-less.** Any PIN makes every browser prompt for it, even with `userVerification: 'discouraged'`.
- **Enroll in Safari on a Mac, never desktop Chrome.** Chrome upgrades a discoverable create on a security key to UV-required and forces PIN setup. `register.js` warns on screen when `detectBrowser` in `key-enroll.js` reports desktop Chrome.
- **Enroll on the production origin.** Credentials are bound to the RP ID (hostname). Keys enrolled on localhost or a tunnel are invisible to the Vercel site. The QR code points at `location.origin`, except from localhost, where it points at `PUBLIC_DEMO_ORIGIN` in `register.js` and shows a warning that the credential will not be found there.
- **Create options** (`createOptions` in `key-enroll.js`, the only copy since the booth page `enroll.html` was retired on 2026-10-12; `fido-test.js` defaults its controls to the same values): `residentKey: 'required'`, `userVerification: 'discouraged'`, `credentialProtectionPolicy: 'userVerificationOptional'` **without** `enforceCredentialProtectionPolicy` (Chrome throws `NotSupportedError` on that pair), `hints: ['security-key']`, `attestation: 'none'`. `enrollKey` records each credential in the `localStorage` list `ishield_enrollments` and builds `excludeCredentials` from it; records the booth page wrote there still count. `webauthnEnroll` in `ishield.js` is a different ceremony (`residentKey: 'discouraged'`, the phone's own Trust Device create) and is not what writes a key for retrieval.
- **Get options** (`webauthnIdentify` in `ishield.js`, which `webauthnAuthenticate` wraps with the expected-user check): empty `allowCredentials`, `userVerification: 'discouraged'`, `hints: ['security-key']`. The empty list is what lets a stranger's phone read the key, and it is what desktop Chrome refuses on a PIN-less key. Phones (iOS any browser, Android Chrome 128+) are the target; desktop Chrome would need an ID list capped at 64 entries, which is not implemented.
- **Phone numbers are bare digits everywhere**: on the key as `user.id`, in the database, in the `?userid=` parameter, in lookups. `normalizePhone` (`register.js`) and `phoneDigits` (`app.js`) apply the same rule: strip non-digits, drop a leading US `1` from an 11-digit number. Format for display only. The user API does not enforce this: the owner's test user carries `512-555-1234`, so `register.js` normalizes the phone it reads back before putting it in the QR.
- **The key is the authority on identity.** After a successful get, `reconcileUserId` in `app.js` compares the typed User ID with the `userHandle` the key returned. A different number stops the flow; a different spelling of the same number is rewritten to the key's form; a key that returns no handle stops it too (since 2026-10-13; before, the typed value stood). Both Enter Game buttons begin with the open get: `login()` always, and `trustDevice` asks the key who it is before writing anything, binding the device through `bindDevice` when the key already holds the typed identity and writing a credential only when the get fails with NotAllowedError (nothing on the key for this site).

## Registration page (`register.html`)

`register.js` is page glue with no SDK or WebAuthn involvement. Register calls `getUserMedia` (`facingMode: 'environment'` as a preference, so a laptop's single front camera is what it gets) and decodes frames on a 150 ms timer until one holds a QR code, then stops the stream before anything else happens. The decoder is chosen once: the browser's `BarcodeDetector` when `getSupportedFormats()` includes `qr_code` (Chromium, backed by Vision on macOS), otherwise the vendored jsQR on a canvas copy of the frame scaled to 640 px wide; Safari has no `BarcodeDetector`, so there it is always jsQR. The decoded text is trimmed and used as-is as the confirmation number: `lookupAttendee` reads `/db/users/conf/:confNumber` (case-insensitive upstream, a single object back, 404 means no attendee), and the page shows name, phone and email with "not on record" for blanks. There is no typed-ID lookup: the secondary button under Register, Manually Enter User, opens the registration form below with no badge, for an attendee without one or a badge that will not scan. No localStorage is touched and no frame leaves the page.

A badge the database does not know opens a form in place of the details: first name, last name, phone, email, and a Register button; Manually Enter User opens the same form with `pendingBadge` null and a different title and hint. `validateAttendee` trims the names, normalizes the phone to bare digits (7 to 15 of them) and accepts an empty email; `saveAttendee` then, when there is a badge, tries `PUT /users/conf/:confNumber` first (the route the owner calls "create by confirmation number"; measured on 2026-10-09 and again on 2026-10-12 it only updates and 404s for an unknown number, but if it ever creates, the record is keyed by the badge), falls back to `PUT /users/:id` when `findUserByPhone` finds the number already there (keeping that record's balance and photo rather than making the duplicate the API would allow), and otherwise `POST /users`. `email` and `confNumber` are sent every time; the API drops both today, so the badge ID, or "Registered manually", is written into `customAttrib`, which it keeps, and the result's `byBadge` (a read by confirmation number afterwards) decides whether the page notes that a rescan of this badge will not find the record. After the save the page continues exactly as for a known badge, with the typed email on screen and "none, entered manually" in the Badge ID row for a manual entry. A live registration on 2026-10-12 confirmed the POST path (userId 5, later found undeletable: both DELETE routes answered 500 for it while fresh throwaway records delete fine).

Once a record with a phone number is on screen, found or just saved, Step 3 is Enroll FIDO Key: `enrollKey` in `key-enroll.js` runs the create for the bare digits with the attendee's name as `displayName`, keeps the entry in the `ishield_enrollments` list, posts it to the dev server's `/credentials` (silently absent in production), and returns warnings (non-discoverable, PIN used, credProtect not level 1, ceremony mismatch), which the page draws under the button. Only after the create does Step 4 draw the QR, from `registerUrl`: `<origin>/?userid=<digits>`, with the deployment substituted for a localhost origin and a warning that a credential written on localhost does not exist there. The phone therefore lands on Login with New off, and the get reads the number back off the key. A failed create leaves the QR hidden and explains the DOMException name with `ERROR_HINTS`. The key step has been exercised only against a stubbed `navigator.credentials.create`. The QR is drawn with the vendored `qrcode-generator` (`createSvgTag`). The exported helpers (`normalizePhone`, `formatPhone`, `registerUrl`, `attendeeName`, `cameraErrorMessage`, `lookupAttendee`, `findUserByPhone`, `validateAttendee`, `saveAttendee`) are pure or take a `fetch` so a Node harness can cover them; the module's top level only registers a `DOMContentLoaded` listener.

## Partner page (`partner.html`)

`partner.js` is page glue around a password gate, a partner strip, the open get and the balance endpoint. The page opens locked: the form checks `PARTNER_PASSWORD` (`Passkeys2026`, in plain text in the module, deliberately: a demo gate, not security), a match stores `partner_unlocked` in `localStorage` so the booth's device stays unlocked across reloads, and Lock in the footer clears it. The strip at the top of the card is drawn from `PARTNERS`, one tile (icon from `partners/`, name under it) per entry, in order: Google, RSA, Swissbit, HID, Ice Cream; the chosen one is highlighted and stored as `partner_booth`, `?partner=<id>` preselects it (case-insensitive, stored, then stripped from the address bar; an unknown id is ignored), and a stored id that no longer exists falls back to the first. The partner is never sent anywhere: the API has no field for it (asked and checked 2026-10-13), so the choice only decides which presets appear and how the flash names the move. Identify runs `webauthnIdentify` (the get above) and `userIdFromHandle` turns the user handle into the User ID (a phone-shaped handle becomes bare digits by the `phoneDigits` rule, any other non-empty handle passes through trimmed, none at all is an error that says to enroll first). `findUserByPhone` (the same function as in `register.js`) reads the record by those digits, and the page shows name, User ID and balance, formatted as points by `formatPoints` (the demo page formats the same field the same way since 2026-10-13; before that it showed dollars), then the partner's presets (`presets` in `PARTNERS`, signed points: `+10`, `+30`, `+70` for the four sponsors, `+50` for Ice Cream; a negative entry would draw red and go through the overdraft check, but none is negative today; faces from `presetLabel`), a Custom amount box, and Add Custom Credit / Cash Out (`+ Custom`) and Deduct Custom Credit / Buy In (`- Custom`), which take the box through `parseAmount` (positive, two decimals at most, up to `MAX_AMOUNT`, a leading `$` and commas tolerated). Each press is one `PATCH /users/:id/balance` through `adjustBalance` (the same function as in `app.js`, by `userId`, never by phone): the API adds what it is sent, so a deduction is negative, and because the API allows an overdraft the page refuses a deduction the balance cannot cover, as `settleAction` does. Every balance button is disabled while a PATCH is in flight, including presets drawn by a partner switch meanwhile. A failed PATCH is re-read by phone, never retried. A number with no record shows a note and no buttons; a database that does not answer leaves the account hidden. This page does not redirect: the first version opened a partner URL with `?userid=`, was replaced by three dollar buttons on 2026-10-12, and by the gate, strip and point presets on 2026-10-13. Desktop Chrome gets the same on-screen warning as the registration page, worded for the get, and a browser without WebAuthn gets a disabled button. The exported helpers (`checkPassword`, `findPartner`, `partnerFromSearch`, `formatPoints`, `presetLabel`, `userIdFromHandle`, `describeGetError`, `parseAmount`, `findUserByPhone`, `adjustBalance`, `fullName`) are pure or take a `fetch`, so a Node harness covers them and the page flow with the DOM, `localStorage`, the get and the API stubbed. A real key went through the deployed redirect version on 2026-10-12; the buttons have run only against the stubs. The logos in `partners/` came from the API owner's site (`sbit.authconcepts.com:3099`); the ice cream is Twemoji's U+1F366, CC-BY 4.0, credited in the SVG.

## Demo flow in `app.js`

Screens are SETUP, LOGIN, SNA, ACTIONS, and EXCHANGE, chosen by `updateUI()` from `STATE.loginID`, the "New" toggle, a pending number check, and the `exchange` state. The toggle picks the ceremony: New on runs `trustDevice()` (the open get first; the iShield **create** only when the key holds nothing, then ZSM enroll); New off runs `login()` (the iShield **get** first, every time, with `reconcileUserId` holding the typed User ID to the key's user handle; then ZSM enroll on an unbound device, or authenticate; before 2026-10-13 the get ran only on an unbound or suspended device). Arriving via `?userid=` sets New from the `new` parameter: the registration QR carries none, so New goes off, because that attendee was just enrolled on a key and must take the get path, not write a second credential; `&new=1` forces New on, so a link can land an attendee with nothing on a key yet on Trust Device (no page emits it today). Either way Passkeys is left as the attendee last set it (on by default), so the binding enrolls a Passkeys+ passkey as well and the Passkey indicator lights. `updateUI` still forces New off and disables the toggle once ZSM is bound for that User ID, whatever the URL said.

Every path that ends in a login passes `ensureNumberVerified(user)` before `STATE.loginID` is set: `trustDevice` after its ZSM enroll, and `login` after the binding enroll on an unbound device, after a Passkeys+-first enroll, and after the plain `authenticate`. Reactivating a suspended device skips it. The gate resolves at once when `sna_verified:<user>` exists. Otherwise the SNA screen comes up with the User ID formatted as a phone number (the status pills under the card are redrawn by `refreshPills` as it appears and again when the number verifies, since `updateUI` does not run until Continue), "Verify my number" runs `verifyNumber` from `sna.js` and colours its step rows as they go, a match writes the marker and shows the status "<phone> Verified" and the four indicators, labelled USB Key, Phone# Verified, Cryptographic Device Binding and Passkey Enrolled since 2026-10-13 (the first from the local marker, the second from the new one, the last two from `checkAllEnrollment`; each row reads true or false as the pills do, with unknown for a key marker this device never wrote), and Continue resolves the gate so the caller carries on into `updateUI`. Cancel resolves it false and the caller returns to the screen it came from, so the check is simply asked for again on the next login; a P2P responder lands back on the confirm screen. `updateUI` keeps the SNA screen up while the gate is pending, and `showScreen` makes the User ID read-only there. The presenter can play IDlayr's other two outcomes once with `?sna=nomatch` or `?sna=unsupported`: the value goes to `sessionStorage`, comes off the address bar, and is consumed by the next check, which then offers Try again. ACTIONS shows the stored check ID and one-time code in a third collapsible block beside the iShield and Passkeys+ challenges. The pill row reads USB Key, Phone# Verified, Device Bound (the ZSM credential), Passkey, then Passkeys+ (the labels since 2026-10-13; ids and code keep `ishield` and `number`).

On ACTIONS, every button runs the ZSM step-up `authenticate` first. P2P Contact Exchange then branches to the EXCHANGE screen (below). Authenticate settles against the user database: `settleAction` re-reads the record by bare-digit phone, refuses the charge on the page if the balance is short (the API allows overdrafts), and sends `PATCH /users/:id/balance` with a **negative** amount, since the API adds what it is sent. The amounts are fixed per action in `ACTION_AMOUNTS`, in points; the P2P entry there is unreachable until it is decided whether an exchange should cost anything, and the other two actions touch no balance. A failed PATCH is re-read, never retried, because the API has no idempotency key. The balance line on the screen is hidden when the User ID has no record, and a missing or unreachable database never blocks the step-up itself. The balance and every charge are formatted as points (`formatPoints`, "1,030 pts"), the same unit the partner booths credit; the page showed dollars until 2026-10-13.

The EXCHANGE screen serves both sides of a P2P Contact Exchange and is driven by the `exchange` object in `app.js`. The initiator's step-up is followed by a create call; the page draws the returned code as a QR of `<origin>/?exchange=<code>` with the vendored generator and polls every 2 seconds until the record has a responder or the server answers 404 (expired). The responder arrives with `?exchange=`: the code goes into `sessionStorage` under `pendingExchange`, the parameter is removed from the address bar, the New toggle is forced off (an attendee with a key takes the login path, as with `?userid=`), and `openExchangeInvite` puts the EXCHANGE screen up at once in its confirm state: the title is "Confirm sharing contact info", a status read names who is asking, and a button of the same wording appears. An expired or already-used code is reported there and dropped. The button runs `confirmExchange`, whose passkey verification is the demo's own `login()` (the iShield touch, then ZSM enrollment on an unbound phone or ZSM `authenticate` on a bound one); `login` ends in `updateUI`, which sees the pending code and calls `completeExchange` with no further prompt. A page that is somehow already logged in gets the ZSM step-up alone, as the action buttons do. Both screens then show the other person's name, phone, and User ID from the record. Done, Cancel, and Log Out all go through `endExchange`, which stops the poll and clears the pending code. `showScreen` hides the New toggle on EXCHANGE throughout and makes the User ID read-only only once `STATE.loginID` is set, so a responder can still correct the number before confirming.

Suspension is a `localStorage` flag (`passkeys_suspended:<user>`); a suspended device requires an iShield touch plus ZSM authenticate to clear it. "Reset Device" wipes `localStorage`, `sessionStorage`, and the `ideem` IndexedDB, keeping only the username; the number-verified marker goes with them, so the next binding runs the SNA check again.

The User ID input carries deliberate password-manager opt-outs (`name="ishield-user-id"`, `data-1p-ignore`, etc.) because iOS AutoFill was offering saved `*.vercel.app` logins over it. Keep them if the field is restyled.
